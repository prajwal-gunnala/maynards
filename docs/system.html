Two projects, one missing wire

MeshAI runs models across devices. The Mesh Compiler measures what settings a device should use for a task and proves the answer against the task's own tests. The compiler already produces a settings file. MeshAI does not read it. That wire is the Ned Capsule.

1 the two projectsred = the only thing missing

Why they are separate repositories. maynards puts GPU backends out of scope for the event build, and two people work in parallel. The compiler writes no engine code: every mechanism it uses already exists in llama.cpp. What it adds is choosing and combining them per device, per task, from measurements, and proving the result.

2

The finding that makes this a compiler — the best setting depends on the task

If one setting were best for everything, a tuner would be a lookup table. It is not. On the same phone and the same model, the GPU reads prompts three times faster and writes words thirty percent slower. So the right answer for a coding agent is the wrong answer for chat — and that is why the output is a file per task, not a global config.

2 CPU against GPU, by taskiQOO 15 · Qwen3-4B · measured 10 Oct

And quality held. 14 of 15 coding problems passed on both, failing the same one (parse_duration). A setting that is faster and fails differently is not a win; this one changed nothing about the answers.

3

The tuner’s loop — how a setting becomes a proven setting

3 tuner loopmulti-objective: two task times at once

Why two objectives rather than one. “Fastest” is meaningless when the GPU helps reading and hurts writing. Scoring both task times at once lets the search find the frontier instead of a single winner, which is what makes a per-task answer possible.

4

Seven layers, and where each one stands

The compiler is organised as layers that each remove a different cost from a repeated task. Two are measured. One is the optimizer this drawing was originally about.

LayerWhat it removesStatus
1Settings per device per taskwrong engine, wrong cache, wrong thread countmeasured on the 4B · agent step −28 to −43%
2Reuse the fixed part of the promptre-reading instructions and files that repeat every callmeasured · repeat request −95 to −98% prompt work
3Guess from what the task already saidone-word-per-step decoding on repetitive outputnext · prior work says the gain is small, so measure
4Smallest model that still passespaying for capability the task never usesnext · one afternoon with the existing gate
5Right-size the memorycontext and answer length allocated and unusednext
6Drop experts the task never routes to~20% of the 30B’s memoryfor the 30B step · pruned files already published
7Split by measured speed, not free memorythe slowest device holding the most layersnot built — this is the optimizer

what layer 2 actually did

Send the same ~1,900-token context seven times with different short tasks. Prompt work per repeat request fell from 48.7–54.8 s to 0.5–1.1 s on CPU, and the whole reply from 50–56 s to 2.1–2.8 s — about twenty times faster. For an agent that re-sends the same instructions and the same files every step, this is the largest single saving found.

and the honest failure inside it

Editing in the middle of the context does not reuse the cache in this llama.cpp build. Checked with both cache formats and with flash attention on and off; the engine log shows no reuse. Only the part before the edit is reused — 1,435 of 1,778 tokens. A known limit for insertions. The fix to try is a prompt layout rule: fixed part first, byte-identical, edits appended at the end.
5

Layer 7 — the split the optimizer would change

Today plan() gives layers in proportion to each device's free memory. The compiler knows something better: how fast each device actually runs a layer for this task. Those are different numbers, and using the wrong one leaves the slowest device holding the most work.

5 layer 7, not builtbar widths illustrative; the two orderings are the point

What it needs, and all of it already exists somewhere

InputWhere it comes from
per-device read and write speed, per taskruns.sqlite — the tuner already stores exactly this
free memory, heat, battery, latencyMeshAI’s control link, every 2 s
layer byte sizes, active fractionread_gguf() already parses the header
which layouts fitplan() already computes this and says “short by N GB”

So layer 7 is not a new subsystem. It is a join: take the speeds the compiler measured, feed them into the splitter MeshAI already has, and score layouts by predicted task time instead of by memory share.

6

The capsule — the file that closes the gap in drawing 1

The compiler's output today is two lines of settings a human copies. As a file the device reads, it becomes the wire.

{
  "capsule_id": "a3f9c1",
  "device":  { "serial": "...8a75", "soc": "Snapdragon 8 Elite Gen 5" }
  "model":   { "file": "Qwen3-4B-Q4_K_M.gguf", "sha_head": "94a16f7a" }

  // one entry per task, because the right answer differs by task
  "tasks": {
    "chat":  { "engine":"cpu",    "threads":6, "ctk":"q8_0", "ctv":"q8_0" }
    "agent": { "engine":"opencl", "threads":6, "ctk":"f16",  "ctv":"f16",
               "ngl":99, "batch":512, "cache_prompt":true }
  }

  "limits":  { "thermal_ceiling":0.85, "min_battery_pct":20 }
  "evidence": { "run_ids":[412,418,431], "gate":"14/15", "baseline_gate":"14/15" }
}

the field that makes it defensible

evidence. Every setting points at the run ids that produced it and the quality gate it passed. A capsule is not an assertion about what is fast — it carries the measurements, so anyone can check it against runs.sqlite. That is the difference between a config file and a result.

what has to change in maynards to read it

Three small things, none of them deep. Engine.kt:47 hardcodes -t cores−2 -c — those come from the capsule instead. The backend needs two .so files in the APK, CPU and OpenCL, because the backend is compiled in, not chosen at runtime; the compiler has already built the OpenCL one. And plan() gains a task name, so it knows which entry in tasks to apply.
