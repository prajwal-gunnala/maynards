1 · What exists today

The stage, not the pitch

A transformer is a stack of layers a token passes through in order, so the layers can live on different machines. Our 48-layer model is cut three ways. Only the token's hidden state crosses each boundary — hidden_size × 2 bytes = 4 KB — because every device already holds its own weights locally.

Why it is usable and not merely clever Pooling solves capacity. Mixture-of-Experts solves bandwidth: the model activates 3.3B of its 30.5B parameters per token, so it reads ~2.0 GB where a dense model would read 18.56 — about 9× less memory traffic. Adding phones adds capacity and almost no bandwidth, because in a pipeline the devices take turns. Both are needed; neither suffices.

2 · Part one — the Ned Capsule

From three fields to a contract new

The planner currently sends this, and nothing else — host.rs:668:

json!({"t": "run", "layers": "9-27", "model": "Qwen3-Coder-30B-A3B"})

Every other decision — which backend, how many threads, how much cache, when to stop for heat — is a constant compiled into the phone. The capsule makes those decisions the planner's output, chosen per device.

The honest caveat The genuinely new capability is per-device backend choice — today both phones run the identical generic ggml-rpc-server. Whether Vulkan beats CPU differs by chip, and nobody has measured it on these two phones. The benefit may be zero or negative. That measurement is itself a deliverable: if the two phones disagree about which backend is faster, that single fact justifies the whole idea.

3 · Part two — remote join by relay

A phone that is not on your cable new

ggml-rpc speaks raw TCP. So this needs no WebRTC and no change to llama.cpp: both sides dial outward to a relay, which splices the two sockets. llama.cpp still believes it opened an ordinary socket to a peer.

The real risk is jitter, not latency Our 94-second Wi-Fi failure had stalls up to 10.5 seconds — that is not latency, it is a stall. Stable 50 ms is fine; a flaky link is not. Which is exactly what part three is for. And an agent task running for seven minutes cannot tell 4 tok/s from 6.8.

4 · Part three — the supervisor

Surviving a device that leaves new prerequisite

This is not currently a degraded case. It is a crash, in three places at once:

WhereWhat happens
Runner.kt:91-94// 4. a helper leaving mid-run ends the run → fail("A helper left") — by explicit design
host.rs:532lost_layers → stop() with "press Start again"
ggml-rpc.cppevery client call wrapped in RPC_STATUS_ASSERT → GGML_ABORT. The process dies. No retry anywhere.

A remote phone on mobile data will drop. So without this, part two is a demo that breaks on stage.

7 · Time, and what gets cut

22–29 hours of work against 20–24 available

The order, and the reasoning behind it

  1. Part 5 first. Three hours, and the results change what is worth optimising afterwards.
  2. Part 2, the relay. Lowest risk, nothing depends on it, and it unlocks the headline.
  3. Part 3, the supervisor. Parts 2 and 3 ship together or not at all — a remote device that kills the run when it drops is worse than no remote device.
  4. Part 4, metering. Independent, low risk, degradable to a single screen.
  5. Part 1, the capsule. Most valuable intellectually, most invasive, and invisible without its UI. Last, because a half-finished capsule still leaves a working mesh — whereas a half-finished supervisor leaves a broken one.
The safety property throughout None of this changes how the model runs. The engine invocation, the layer arithmetic and the layer store are untouched. At every point the fallback is the mesh that already works.

Verification

  • cargo test --release and ./gradlew testDebugUnitTest assembleDebug green at every commit.
  • The relay tested laptop-to-laptop first, before a phone is involved.
  • The supervisor tested by actually pulling a cable mid-generation, repeatedly — not simulated. This is the feature most likely to work once and fail twice.
  • Capsule manifests captured before and after a re-plan, so the mechanism is evidenced rather than described.
  • A full dry run of the demo with at least three hours left on the clock.

8 · The centrepiece — the mesh paints

A 20-billion-parameter image model, split across two phones new

stable-diffusion.cpp officially supports the ggml RPC backend — merged June 2026, a dedicated guide, and a fix merged on 9 October 2026. It reuses llama.cpp's own rpc-server, which is already running on both phones. So the same mesh that answers questions can generate pictures, and the architecture stops looking like an LLM trick and starts looking general.

A claim that must change when this runs Our headline has always been "only 4 KB crosses the link." In diffusion the state crossing a boundary is the entire spatial latent, every patch token, every step — roughly 30 MB, about 7,000× more. The honest and still-strong line: "the state between stages is small enough that the link disappears into the compute — 3–12% overhead — and the model simply does not fit on any single device." Saying "4 KB" while the image demo runs is a falsifiable claim someone will check.

The four things most likely to cost us the day

TrapWhat to do
GGML_MAX_NAME mismatch — transfers fail without it Rebuild rpc-server on every device with -DCMAKE_C_FLAGS=-DGGML_MAX_NAME=160 and the C++ equivalent. The client uses -DSD_RPC=ON, not GGML_RPC.
Version skew Check out the llama.cpp commit pinned in ggml/scripts/sync-llama.last. Pin sd.cpp after PR #2115 — issue #2114 broke HEAD on 9 Oct.
A 9-minute cold start on stage — sd.cpp pushes weights from the client; the phones do not read them locally as they do for the LLM Launch rpc-server -c for the on-disk tensor cache, and pre-warm before the room sits down. 13 GB at 24 MB/s is nine minutes.
Minutes per image Use a 4–8 step distilled variant (Qwen-Image-Distill / Flash). Step count is the single biggest lever on both wall-clock and crossings.
Why this is the novelty as well as the spectacle Nobody has run a 20B image model split across phones. It is visual, it needs no explanation, and it proves the architecture generalises past language models — which is a stronger claim than any protocol change. And it is insurance: a vision-language model on the existing mesh is 2–3 hours and near-zero risk, so there is a fallback that still shows a picture driving the demo.
What the same research rules out — state these plainly Video is not reachable (Wan 2.2 at 480p is ~335 MB per crossing and hours of phone-CPU compute). Vector search does not fit — it is random access over the whole dataset, so the link becomes the inner loop, not a boundary crossed once. Fine-tuning over RPC is unsupported. General RAM rental fails: a page fault to a phone is ~30,000× slower than local DRAM. The honest claim is distributed memory capacity for sequential, memory-bound inference — and never "distributed compute", because three phones have less usable compute than one mid laptop.
