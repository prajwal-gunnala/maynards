A.1

The cost model — everything else is built around this

An optimizer is only as good as its ability to predict. Before any search, candidate generation or capsule emission, there has to be one function that takes a proposed layout and returns how long a token will take. This is that function, and every term in it is either measured on our hardware or read from the model file.

A.1 cost model, annotatedsources: results/REPORT.md, docs/measurements.md

The one calibration that validates it. Before trusting this function on anything new, it must reproduce a figure we already have: the current three-device split measured 6.8 tok/s. If the model predicts that within a reasonable margin, it can be trusted to rank layouts. If it does not, the bandwidth estimates are wrong and nothing downstream is meaningful.

A.2

System layers — where each piece sits

Not a flow of control but a stack of responsibilities. Reading upward: silicon, the operating system's constraints, the inference engine, the transport, the control plane, the planner, the public interface, and finally products that consume it. The origami tool sits in the top band and knows nothing about any band below the API.

Why this is the important drawing. The band at the top is the argument. A product can be built against a single HTTP address and never learn that its model is spread across two phones — which is what makes this infrastructure rather than a demonstration.

B.1

The optimizer — how it gets built, stage by stage

The planner today makes one greedy pass: drop unusable devices, sort the rest by free memory, hand the phones their share from the last layer backwards. It never considers an alternative. An optimizer enumerates alternatives and scores them, and the useful discovery is that the search space here is small enough that no clever algorithm is needed.

B.1 optimizer data flowstages 5 and 6 are new in this window

Built in this order, for this reason

StageWhat it doesWhy it is in this position
0 · profileMeasure each device's effective bandwidth once, by running a known model alone and timing it.First, because everything downstream is noise without it. One data point already exists: an 8B dense model alone on a phone at 11.8 tok/s implies ≈55 GB/s.
1 · enumerateDevice subsets × cut points. Around 1,200 candidates.No heuristics needed. Generating all of them is cheaper than being clever about which to skip.
2 · filterDiscard anything that cannot physically run.Before scoring, not after — scoring an infeasible layout wastes work and risks selecting it.
3 · scoreApply A.1 to each survivor.The only stage with a model in it. Everything else is bookkeeping.
4 · selectMinimise predicted time, or memory, or imbalance.Separated from scoring so the objective can change without touching the model.
5 · emitOne capsule per chosen device.The output is a contract, not a layer range. Part D.
6 · calibrateCompare prediction to reality, correct the profile.Last, and it closes the loop. Without it the optimizer is confident and wrong forever.

what makes this an optimizer rather than a heuristic

Three properties, and the current planner has none of them: it considers alternatives it will not choose; it can explain its choice, because every candidate has a score; and it gets less wrong over time, because stage 6 feeds measured reality back into the profile that stage 3 depends on.

the honest limit

A predicted layout still has to be enacted by restarting the engine — llama-server is told the split at launch and has no way to change it. So the optimizer chooses between runs, not during one. On a seven-minute agent task a 70-second re-plan is affordable. Mid-sentence it is not, and the specification should not imply otherwise.

D.1

The Ned Capsule — the file on the device

A file. Written to the device's own storage. The device reads it and starts its engine from it. No weights: the device already holds all 144 layer tensors, so a new capsule costs a restart, not a 13 GB transfer.

/data/data/ai.maynards.mesh/files/capsule/current.json     what it is running now
/data/data/ai.maynards.mesh/files/capsule/previous.json    kept, so two can be diffed
/data/data/ai.maynards.mesh/files/capsule/rejected.json    written when validation fails

Two halves, and only one of them is the device's

The device cannot choose its own layer range. llama-server on the host splits the model with --tensor-split, which takes proportions. So the host decides, and the capsule records what was decided so the device can check it and so it can be audited.

What the device does, in order

1  receive capsule over the control link
2  write it to capsule/incoming.json
3  validate
      model.sha_head matches the local file           else reject: wrong model
      every hash in layers.hashes[] is in the store   else reject: missing N tensors
      free memory ≥ memory.advertise_mb + reserve     else reject: short by N MB
      battery ≥ limits.min_battery_pct                else reject: battery
      heat ≤ limits.thermal_ceiling                   else reject: too hot
4  on reject → write capsule/rejected.json with the reason, reply, stop
5  on pass  → stop the current engine
6  mv current.json → previous.json ; mv incoming.json → current.json
7  launch the engine from current.json
8  reply {ok, capsule_id, address}
9  report telemetry against the field list in the capsule

why validation lives on the device

The host plans from telemetry up to two seconds old. The device knows its own state now. A capsule the device cannot honour is rejected with a reason before the engine starts, instead of failing during generation.

two fields cost real work

runtime.backend needs two binaries shipped in the APK — libmesh_rpc_cpu.so and libmesh_rpc_vulkan.so — because the backend is compiled in, not selected at runtime. And nobody has measured which is faster on these phones, so the field may turn out to be worthless. layers.hashes[] needs the host to read the tensor names for a range out of the GGUF header, which read_gguf() already parses.

what makes it an artifact and not a message

It is on disk. Pull it with adb pull and read the contract. The device restarts and re-enacts itself without asking the host. Two capsules diff. And a phone that belongs to a stranger carries, in writing, exactly what it agreed to do.

F.1

A product on top — packaging design for a small manufacturer

The test of whether this is infrastructure: can something be built against it that knows nothing about it? The packaging tool below speaks only HTTP to one address.

F.1 consumer applicationcatalogue-bounded output · verifiable against its source

Three justifications land at once here, which is unusual. It needs the vision model, so a small model will not do. It needs reasoning over material and compliance constraints, so the big model is earning its place. And the input is an unreleased product design, so it genuinely cannot be sent to an API — which is the one argument nothing else in this field can make.
